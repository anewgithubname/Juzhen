# Python 编译（`jz.compile`）计划

状态：第 1、2、3 步已完成（原地运算入口；记录和生成；复用中间矩阵）。第 4 步起未开始，其行数是估计。

## 1. 目标

用户照常写 Python 函数，加一行 `@jz.compile`。第一次调用时记下函数里的矩阵运算，整理成一串最省的 Juzhen 调用，以后每次调用直接执行这一串。

要得到的好处，按先后：

1. 用完就丢的中间矩阵被原地复用，不再每步新开一个。
2. 广播（`A - row`）不再先铺出一个完整矩阵。
3. 相邻的逐元素运算合并成一遍扫描（最后做，做法看数据再定）。

不做的事：

- 不做独立的脚本语言，不做文本格式、解析器。
- 不改变没有加标记的代码的行为和速度。
- 不让内核本身变快。矩阵乘、卷积、`max`、`sum` 的速度不变。

## 2. 用户看到的样子

```python
@jz.compile
def step(W, X, Y, lr):
    P = jz.tanh(X @ W)
    E = P - Y
    G = X.T @ (E * (1 - P * P)) / X.shape[0]
    W -= lr * G
    return jz.mean(E * E)
```

`step.explain()` 打印整理后的结果。上面的函数会变成：

```python
def step(W, X, Y, lr):      # W 784×10, X 256×784, Y 256×10
    t1 = matmul(X, W)
    tanh_(t1)               # P，占用 t1
    t2 = sub(t1, Y)         # E
    mul_(t1, t1)            # P * P，P 之后不再用
    rsub_(t1, 1)            # 1 - P * P
    mul_(t1, t2)            # E * (...)
    t3 = matmul(T(X), t1)
    div_(t3, 256)
    mul_(t3, lr)            # G 之后不再用
    isub(W, t3)             # 用户自己写的 W -=
    mul_(t2, t2)            # E 之后不再用
    return mean(t2)
```

带下划线的是原地运算。不编译时这个函数新开 10 个矩阵，编译后新开 3 个（`t1`、`t2`、`t3`）。

## 3. 做法

分三部分，前两部分是纯 Python。

**记录。** 第一次调用时，把传进来的矩阵包一层"代理"再交给用户的函数。代理里面装着真矩阵，每做一个运算就真算一次，同时在表里记一行。所以第一次调用的结果就是正常结果，形状也都是真的。

**整理。** 拿到整张表后，算出每个中间结果最后一次被用在哪一行，决定哪些运算可以原地做。

**生成。** 把整理后的表写成一个 Python 函数（就是上面 `explain()` 打印的那个），以后的调用直接执行它。它调用的是绑定层里新加的一组原地运算入口，这是唯一要写 C++ 的地方。

### 和我之前说的两处不同

**记录放在 Python，不在绑定层的 50 个入口里加记录点。** 原因是安全：用代理的话，凡是代理没有实现的操作都会直接报错；在绑定层加记录点的话，漏掉一个入口就会悄悄记出一张错的表，以后每次调用都算错而不报错。

**先生成 Python 函数来执行，不先写 C++ 执行器。** 原因：

- 网络调用自然就能用。`nn.py` 靠 Python 这边的记录把损失的梯度和网络的那次调用对上，生成的 Python 函数照常调用 `net(x)`，这些记录照常更新。写 C++ 执行器的话这是最难的一步。
- C++ 的工作量从"为 50 种运算写执行器"降到"加一组原地运算入口"。
- 代价：每一步运算仍然经过一次 Python 调用，这部分开销和现在一样，没有省。它只对循环里的很小的矩阵有意义。以后如果实测说明值得，再把连续的一段纯矩阵运算交给 C++ 一次执行（第 7 步，可选）。

## 4. 规则

第一版能用的：

- 参数：矩阵、数、numpy 数组（只能原样用作下标）、True、False、None、字符串，以及它们的列表、元组和字典。网络对象等到第 4 步。
- 矩阵的全部运算符和 `jz.` 下所有接收矩阵的函数，`.T`、`.shape`、切片。
- 函数里新建矩阵：`jz.zeros`、`ones`、`randn`、`rand` 和 `_like`。每次调用都重新生成。
- 用户自己写的原地运算（`W -= ...`）。
- 次数固定的循环（会被展开）。

会报错并用一句话说明的：

| 写法 | 原因 |
|---|---|
| 对中间结果做 `float()`、`.item()`、`.numpy()`、`if A:`、`print(A)` | 值离开了矩阵运算，以后的调用无法重现 |
| 函数里用了不是参数传进来的矩阵（全局变量） | 分不清它是固定的还是每次会变的；改成参数传入 |
| 函数里调用 `jz.array(...)` | 里面的 numpy 数据只在第一次算过一次 |
| 对小数参数做加减乘除和乘方以外的事（`math.sqrt(lr)`、`if lr > 0`） | 同第一条；开方写 `lr ** 0.5`，要按它分支或循环就传整数 |
| 把中间结果存到函数外面（全局列表、对象属性），之后再用 | 以后的调用不会再存；应当作为返回值返回 |

其他要知道的：

- 小数参数（如 `lr`）在生成的函数里仍是变量，换一个值不需要重新记录。
- 整数、布尔值、字符串、None 被看作函数本身的一部分，按值各记一张表（所以 `range(n)` 可以用）。一个函数记到 32 张表时会给一次警告，提示把每次都变的整数改成小数传入。
- 函数里自己算出来的普通 Python 数（`math.pi * 2`、`len(...)`）只在记录时算一次。
- 每种"参数形状加设备"的组合各记一张表。最后一个批次变小时会重新记录一次。
- 不是矩阵运算的 Python 代码（计数、普通的 `print("...")`）只在记录时执行。

## 5. 什么时候可以原地复用

一个中间结果可以被后面的运算占用，必须同时满足：

1. 它是表里的矩阵运算新开出来的。传进来的参数、网络调用返回的矩阵永远不占用。
2. 它没有被返回，也没有传给过网络或损失函数（它们会留着这个矩阵，反向传播要用）。
3. 后面没有任何一行再用它，也没有再用和它共用存储的 `.T`。
4. 这一步运算的结果形状和它相同，并且另一个操作数不是它自己的转置。

运算顺序保持不变。所以在合并运算之前，编译后的结果应当和不编译时逐位相同，这是每一步的验收标准。

### 第 1 步是一道关口

第 1 步做完就能手写出"编译后应该是什么样"的代码并计时，这就是第 2、3 步的收益上限。如果上限很小（比如 CPU 上不到 20%），就不该继续做第 2、3 步，而应该重新考虑：要么直接去做合并运算，要么停。

库里已有原地版本的运算：加、减、逐元素乘、数乘、数除、取负、`exp`、`tanh`、`square`、`sqrt`。个别后端缺个别函数的原地版本（比如 `log`），那里先退回普通运算，结果一样，只是没有提速。

### 在哪里验证

- 每一步：本机 CPU 和 ROCm。
- 第 1、3、4 步：另外在 4090（CUDA）和 M2（Metal）上跑一遍测试和计时。

## 7. 预期收益

从已有的 `A + B` 和 `A += B` 计时推的，单步逐元素运算：

| 设备 | 预期 |
|---|---|
| x86 的 CPU | 最多约 1.7 倍 |
| M2 的 CPU | 约 7% |
| CUDA | 约 15% |
| ROCm、Metal | 基本没有 |

整个函数的提速会比这小，因为矩阵乘这类运算不受影响。真正的数字要等第 1 步。

### 第 1 步的实测（2026-11-28）

同一个公式，"照常写"和"用原地运算入口手写"（即编译后应有的样子）的用时之比。结果都逐位相同。

| 公式 | 本机 CPU | 4090 那台的 CPU | CUDA（4090） | ROCm（8060S） |
|---|---|---|---|---|
| `sum((A - B) * (A - B))`，4096² | 1.6 倍 | 2.9 倍 | 2.0 倍 | 1.5 倍 |
| `A + 0.5 * B`，4096² | 1.25 倍 | 1.45 倍 | 1.2 倍 | 1.1 倍 |
| `1 / (1 + exp(-A))`，4096² | 1.07 倍 | 1.2 倍 | 1.6 倍 | 1.2 倍 |
| 手写的 Adam 更新，4096² | 1.1 倍 | 1.05 倍 | 1.1 倍 | 1.0 倍 |
| 第 2 节的 `step`，4096×1024→1024 | 1.0–1.1 倍 | 1.0–1.1 倍 | 1.07 倍 | 1.03 倍 |
| 高斯核矩阵，4096×4096 | 1.1–1.2 倍 | 1.02 倍 | 1.3 倍 | 1.14 倍 |

1024² 及更小时，CPU 上大多是 1.0–1.1 倍，CUDA 上 1.1–1.35 倍。Metal 还没有测（M2 当时连不上）。

结论：收益集中在大矩阵上的纯加减乘。含矩阵乘的函数几乎不变；含 `exp`、`tanh` 的函数在 CPU 上也几乎不变，因为 CPU 上这两个函数本身很慢（4096² 的 `tanh` 要 160–180 毫秒，一次加法只要 4 毫秒），时间都花在它们身上。

### 第 2 步的实测（2026-11-28）

- 编译前后逐位相同：本机 CPU 和 ROCm、4090 的 CPU 和 CUDA 上，`python/tests/test_compile.py` 里约一百个运算和六个基准公式都一致。Metal 没有测。
- 每次调用的额外开销：约 0.9 微秒（三个参数，本机 CPU），用来核对参数的形状。对 4×4 的矩阵，一个三步运算的函数从 1.2 微秒变成 2.1 微秒；矩阵稍大就可以忽略。
- 和计划不同的地方：没有做 `static=` 选项，改成"小数是变量，整数是函数的一部分"这条规则。

### 第 3 步的实测（2026-11-28）

整理记录时做三件事：同一个式子写了两遍只算一次；结果放进之后没人再读的中间矩阵；广播时结果放进铺出来的那个矩阵（这一条在绑定层，不编译的代码也受益）。编译后和照常写逐位相同。

`python/benchmarks/compile_bench.py`，照常写的用时除以编译后的用时：

| 公式 | 新开的矩阵 | 本机 CPU | 4090 那台的 CPU | CUDA（4090） | ROCm（8060S） |
|---|---|---|---|---|---|
| `sum((A - B) * (A - B))`，4096² | 5 → 3 | 1.57 倍 | 2.93 倍 | 1.96 倍 | 1.49 倍 |
| `A + 0.5 * B`，4096² | 2 → 1 | 1.28 倍 | 1.40 倍 | 1.19 倍 | 1.00 倍 |
| `1 / (1 + exp(-A))`，4096² | 4 → 1 | 1.14 倍 | 1.14 倍 | 1.56 倍 | 1.24 倍 |
| 手写的 Adam 更新，4096² | 11 → 7 | 1.11 倍 | 1.02 倍 | 1.09 倍 | 1.03 倍 |
| 第 2 节的 `step`，4096×1024→1024 | 13 → 5 | 0.99 倍 | 1.00 倍 | 1.06 倍 | 1.02 倍 |
| 高斯核矩阵，4096×4096 | 11 → 6 | 1.25 倍 | 1.03 倍 | 1.34 倍 | 1.12 倍 |

和第 1 步手写的上限一致。256² 到 1024² 时大多在 0.9 到 1.4 倍之间，个别情况略慢于照常写：

- 每次调用要核对参数形状，约 1 微秒。
- 在 4090 那台的 CPU（5800X3D，gcc 13）上，矩阵能放进缓存时，取负和数乘的原地循环比新建结果的循环慢约 1.4 倍（加一个数的原地循环反而快 2 倍），原因没有查清；给指针加 `__restrict` 没有用。本机的 CPU 没有这个现象。

## 8. 风险

- **收益可能不够大。** 所以有第 1 步的关口。
- **规则太严，用户常写的函数编译不了。** 第 2 步完成后拿 `python/examples` 里的例子试，统计有多少能直接加标记。
- **悄悄算错。** 靠三样东西防：代理没实现的操作一律报错；原地复用的四个条件；每一步都和不编译的结果逐位比较。
- **记录用的全局状态不支持多线程同时记录。** 第一版写明这一限制。
